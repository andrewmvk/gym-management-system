# Technical Architecture

## 1. Stack Overview

| Layer | Choice |
|---|---|
| Language and tooling | TypeScript 7 (the native compiler) in every workspace, pnpm workspaces |
| Frontend framework | Next.js, TypeScript (`.tsx`) |
| Styling / UI | Tailwind CSS + shadcn/ui (charts through shadcn's Chart component, Recharts underneath) |
| Backend framework | Node.js + Express (tRPC HTTP adapter) |
| API layer | tRPC (end-to-end typed, shared types between frontend and backend) |
| ORM | Drizzle |
| Database | PostgreSQL |
| Auth | Custom JWT, delivered via httpOnly cookie (identity only - no role claim) |
| Authorization | CASL (`@casl/ability` on both apps, `@casl/react` on the frontend), policy-driven via `d_user_policy`/`f_user_policy_on_user`, with policy groups (`d_user_policy_group`/`f_user_policy_group_on_user`) bundling them (see §11) - no fixed role field |
| File storage | Local disk via Docker volume (path/URL stored in Postgres) |
| AI provider | OpenRouter API, using a free-tier model (configurable) |
| Email | Real transactional provider (e.g. Resend) for the registration e-mail with the login link |
| Face recognition | Face detection/embedding library (`@vladmandic/face-api`, a maintained fork of face-api.js; the backend runs it on the TensorFlow.js WASM backend). The registration reference embedding is computed on the backend; the kiosk computes its probe embedding in the browser and runs the 1:N match against the embedding dataset. Both sides must use the same model and weights (see §5) |
| Containerization | Docker Compose: two containers, `frontend` and `backend` (the Node API and PostgreSQL run together in the second one). This split is a course requirement |

```mermaid
    end

    end
    FE -- tRPC over HTTP, JWT cookie --> BE
    KIOSK -- fetch embeddings dataset<br/>KIOSK_API_KEY --> BE
    KIOSK -- report matched memberId --> BE
    BE -- SQL via Drizzle --> PG
    BE -- REST call --> EXT[External Turnstile REST API<br/>(pre-existing, admin-configured)]
    BE -- API call --> AI[OpenRouter API<br/>free model]
    BE -- API call --> MAIL[Email provider<br/>e.g. Resend]
```

Two containers are orchestrated via `docker-compose.yml`: `frontend`, and `backend`, which runs both the Node API and PostgreSQL (one container for the front and one for the back plus database, as the course requires). The two processes in the second container are started by an entrypoint script or a process supervisor; the exact mechanism is an implementation detail of the base setup. The kiosk is the same Next.js frontend app running in a dedicated route/mode (not a third container), but is conceptually a separate, less-trusted client since it's the one physically exposed at the gym panel. The backend container mounts a volume for uploaded files (reference photos and exam attachments) and one for the PostgreSQL data directory.

This is a decoupled architecture (frontend and backend are separate deployables), which is why tRPC is used over plain Next.js API routes - it preserves end-to-end type safety across the network boundary between the two containers, and the frontend/backend still share TypeScript types (e.g. via a shared package or by importing the backend's router type).

## 3. Authentication Flow

1. Member/trainer/admin logs in via a tRPC mutation on the backend.
2. Backend verifies credentials (bcrypt-hashed password). A member whose membership is `inactive` cannot log in: after a correct password (so the message cannot be used to probe which e-mails exist) the login fails with "Your membership is inactive. Ask the front desk to reactivate it." (FR-40, RN-15). Otherwise it issues a signed JWT containing `{ userId }` - no role. Permissions are never embedded in the token; they're resolved fresh from the database on every request (see §11).
3. JWT is set as a cookie with `httpOnly` and `sameSite=lax` always on; `Secure` is set conditionally - only when `NODE_ENV=production`. Local Docker Compose demo runs use plain HTTP, and a `Secure` cookie would silently never be sent/set by the browser in that case, so it must not be hardcoded on.
4. Frontend includes credentials on every tRPC request (`fetch` with `credentials: 'include'`); CORS on the backend must allow the frontend's origin with credentials.
5. Backend tRPC context middleware verifies the JWT on every request, attaching `{ userId }` to `ctx`, then builds a CASL `Ability` for that user from their active policy grants (§11) and attaches it as `ctx.ability`. Procedures check `ctx.ability.can(operation, resource)` as needed - there is no role to branch on. The session load returns no session (null) for a member whose membership is `inactive`, so a cookie issued before the lapse stops working at once and the member is treated as signed out everywhere.
6. No login/authenticated route exists before registration completes (see FR-9) - the JWT is only issued once an account exists and has a password set, and registration creates the account and the password in the same request (see "Registration" below).
7. Trainer/admin accounts are never created via a login-adjacent registration mutation - they only exist via the seed script (see §8). An existing account's policies and groups (including whether it belongs to the trainer/admin group) can later change through the Admin policy-management feature (FR-43) without ever creating a new account.

**Registration**: a person becomes a member only by registering at the physical gym (FR-1, FR-57). The restriction check and the acceptance decision are made in person by a staff member, off-system, and leave no record. The registration page (`/signup`) is meant to be reachable only from the gym's own devices or network, but this is enforced only on paper: there is no intranet restriction, IP allowlist or staff-issued token, and building one is explicitly out of scope for this academic project. The wizard has four steps, Details, Consent, Photo, Password, and keeps everything in the browser until the last one; abandoning leaves nothing stored. The final submission is one backend request that carries name, phone, e-mail, birthdate, optional gender, the consent, the reference photo and the password (minimum 8 characters). In one transaction the backend records the consent (before the embedding, RN-12), computes the embedding from the photo (a photo with no face or several faces rolls everything back), stores the raw photo on the upload volume, hashes the password, creates the `d_users` row with an active (mock) membership and adds the user to the `member` policy group, then starts the session. A registered e-mail is refused (`d_users.email` is unique); there is no rejected or pending state. After the request succeeds, the registration-completed hook sends the e-mail with the login link (§7).

## 4. AI Integration

- All AI calls go through the **backend**, never directly from the frontend - this keeps the OpenRouter API key server-side only. There are exactly two AI purposes: `plan` (training plan generation and adjustment) and `chat` (the chat assistant). Deciding who may be a member is not an AI task: it happens in person at the gym (FR-57), so there is no aptitude, health-screening or certificate purpose.
- The AI module carries **text only**: no images or files ever reach the model. This is why a member's medical exams are entered as typed findings (name, optional date, findings summary) and why an attached exam file is never read by the AI; the file is optional supporting material kept with the entry.
- The specific free model is configurable via an environment variable (e.g. `OPENROUTER_MODEL`), since OpenRouter's free-model lineup changes over time; the code should not hardcode a specific model id in business logic.
- Each AI call is a **stateless request** built from context assembled server-side each time: the member's profile, onboarding data, structured history/fact log, and (for plan generation) the curated exercise/equipment catalog. There is no server-side conversation/session object for the chat - this matches FR-25/FR-26.
- **Plan generation context** (FR-15): the plan prompt carries the member's age, the onboarding submissions (the newest is the current truth, older ones only add history that it does not contradict: goals, physical information, physical conditions, medications and exams), the remembered facts that are not resolved (newest first; `resolved_at` facts are skipped, and injuries and medication changes are always given in detail, however old, never folded into an "older events" count; a wish for more or less of a muscle and each plan the member applied through the coach are among them, as `plan_adjustment_request` facts the prompt tells the model to follow), the last 14 days of plans with their exercises, sets x reps, load, whether each was done and the check-in dates, the member's latest trainer notes and edits (the last 5, as guidance from their trainer), and the demand other members' plans already place on that date. Demand is counted in plans, not exercises: the number of other members' plans (the member's own excluded) that use each piece of equipment and the muscle load those plans add, so a broad goal is spread across different equipment and overloaded equipment is avoided. Safety, injuries, medication, exams and the member's plan requests always win over the spreading. The catalog lines, restricted to exercises available now, close the prompt. The remembered facts in this prompt are only the confirmed ones (`confirmed_at` set, FR-27), and they include the member's own manual edits of sets, reps and weight (`manual_plan_edit`, FR-68). Plan generation streams: each exercise is forwarded as the model finishes it, but nothing is saved until the whole answer has validated.
- **Muscle vocabulary in prompts** (see §12): every catalog line the AI reads is `id | name | primary: ... | secondary: ...`, using the muscle ids of the shared registry, and there is no separate muscle focus: what the member wants emphasized reaches the prompts as the remembered `plan_adjustment_request` facts. The system prompts say such a request steers the balance of the plan (more exercises and sets for a muscle the member wants more of, fewer for one they want less of) but is only a preference: injuries, conditions and safety override it, and a plan is never built from it alone. The deterministic placeholder generator ignores it (one exercise per lead muscle in registry order, three sets each), so the demo works without a model. The six muscle groups (chest, shoulders, back, arms, core, legs) are defined once in the shared registry (`MUSCLE_GROUPS`, every muscle in exactly one group); a chat mention of a group or of the whole distribution gives the model the plan's weighted sets per group and per muscle and, for a group, candidate exercises for its least worked muscles first.
- **Chat response shape** (FR-63): one JSON object whose keys are `reply` (the text), and, only when useful, `facts`, `planProposal`, `exercisePicker`, `exerciseExplainer`, `safetyWarning` and `quickReplies`. The model never writes the changes of a proposal: it returns the full exercise list for the date and the server rebuilds everything the member sees. For each part the backend checks that exercise ids exist and are available (a past-day correction may use any catalog exercise), drops duplicates, recomputes the diff against the saved plan of that date (a past date with no plan falls back to the plan date being discussed), computes injury conflicts itself from the muscles tagged on the member's injuries (FR-28, FR-67) and merges them with the model's own warnings (the injury warning wins), and reads each part leniently (an exercise or a warning that does not fit is left out, a missing date or summary falls back to the plan being discussed, numbers written as text are read, so one slip never turns a whole proposal into a silent nothing; and when a proposal the coach wrote cannot be used, the reply says so instead of letting the text claim a change). Each proposal carries a `memoryNote`, the one short line remembered when it is applied (see Applying a proposal). A picker is checked against the server-prefiltered candidates for the muscle the member pointed at, and a safety warning's alternatives against availability and injuries. A proposal that changes nothing is dropped. Facts are stored after the whole answer validates: an injury or a medication change is stored pending and returned to the panel as a `facts` block (see FR-27), every other fact is stored confirmed at once and not shown in the thread, and a request for a plan is not stored as a fact while the answer carries a proposal, because the plan is remembered when it is applied. What the member pointed at (`mentions`: exercises, muscles, muscle groups, the whole distribution) and the draft they are looking at (`draft`) are part of the request, so the server stays stateless.
- **Read-only tools** (FR-25): the chat call may carry tools, each bound to the signed-in member when it is built (`chat/tools.ts`): `getExerciseDetails`, `searchExercises`, `getWorkoutHistory`, `getTrainerNotes` and `getEquipmentStatus`. There is no write tool: the AI never writes to the database (RN-18). The model's free-tier endpoint is not assumed to support native function calling, so the protocol is plain JSON mode: the model answers with only `{"toolCalls":[{"name","arguments"}]}`, the backend validates each call against the tool's zod input, runs it and appends the result as a user message, and asks again; a failed or unknown lookup is reported to the model as text, never thrown. A request has at most four model calls in total, and the events of a tool turn are never forwarded to the client.
- **Applying a proposal** (FR-21, FR-65): `chat.applyDraft` takes the final draft (date, exercises, the memory note, the safety warnings the member accepted) and, in this order, checks the exercises against the catalog and availability, recomputes injury conflicts and returns `needs_acknowledgement` if one was not accepted, applies the overwrite guard (a trainer edit or ticked exercises returns `needs_confirmation`, FR-22), replaces the plan in place through the plans repository (keeping the ticks of exercises that remain, or the stated ones for a past day), writes the change log row (`f_plan_changes`, kind `coach`, with the accepted warnings) and remembers the plan as one confirmed `plan_adjustment_request` fact whose description is the coach's memory note (the request itself when there is none). No AI call is made.
- **Failure handling**: OpenRouter's free tier is rate-limited and can be unreliable. Any transient failure, timeout, or rate-limit response on a plan-generation or chat call surfaces as a normal "AI is temporarily unavailable" error to the member rather than a raw exception, and is never coalesced into a real outcome (RN-01). An AI failure never produces a plan: when the live AI returns nothing usable (a failure, or an answer with no usable catalog exercise), generation fails and no plan is saved (FR-59). The deterministic placeholder generator is used only when the generator mode is `placeholder`, never as a fallback for a failed live call.
- **Single wrapper and mock mode**: every call goes through one module (`apps/api/src/modules/ai/`) that requests JSON output, validates it against the caller's zod schema, times out after 30 seconds, and retries once only on invalid output; it reports `unavailable` or `invalid_output` as data and each caller maps that to its own state. `AI_MODE=mock` skips the network and returns deterministic fixtures: an empty plan (the placeholder generator builds the plan) and a canned chat reply with no facts and two suggested replies.
- **Streaming runner** (FR-70): next to the one-shot runner, the AI module has `streamStructured`, an async generator that asks OpenRouter for a streamed answer and yields events plus one final result. An incremental JSON reader (`json-stream.ts`) reads the object as chunks arrive and reports the top-level keys, the growing text of a string value, each completed top-level value and each completed element of a top-level array; text before the first brace and after the closing brace (a code fence) is ignored, and malformed text only stops events, because the complete text is always validated against the caller's schema afterwards. The timeout is an idle one (30 seconds since the last chunk). Keys the schema does not know are not forwarded, and the answer is retried once on invalid output only when nothing has reached the caller yet. A stream that fails or ends invalid yields an `unavailable` or `invalid_output` result, never an exception. Mock mode streams its fixture through the same event shape.
- **Streaming transport**: the web client uses the tRPC streaming batch link, which answers ordinary calls as before and also carries procedures written as async generators. Three procedures yield events: `chat.send` (text deltas, then blocks), `plans.generateToday` (an `exercise` event per exercise as it is written, then `done` with the saved plan or the `needs_confirmation` result) and `onboarding.submit` (`saved` with the submission, then the plan's `exercise` events, then `done` with `built`, `kept` or `failed`). The ability check runs first, and a failure after streaming began ends the stream with the usual error; the callers save nothing until their answer has fully validated (RN-19). One HTTP test (`trpc/streaming.test.ts`) proves the events reach a real client through the Express adapter.
- **Generator modes**: `PLAN_GENERATOR` is `ai` or `placeholder`. Unset, it means `placeholder` when `AI_MODE` is `mock` and `ai` otherwise. In `ai` mode the plan comes from the model through the wrapper; in `placeholder` mode the deterministic generator builds it, so the demo works without a model.
- **Plan safety on regeneration** (FR-22, FR-59, RN-06, RN-16): regenerating or editing a plan keeps `completed` for the exercises that remain (matched by exercise). Regenerating a plan that a trainer edited, or that has ticked exercises, first returns a `needs_confirmation` result carrying the `reason` (`trainer_edited`, which takes precedence, or `has_completed`) and `completedCount`; the member must confirm before anything is replaced. Onboarding-triggered auto-regeneration never overwrites such a plan: it skips it. A plan dated before today is history (RN-17): trainers cannot edit it (a note can still be added), and it is not re-filtered by equipment that went down later; only today and later are.

## 5. Face Recognition & Embedding Distribution

- Reference photos captured at registration are processed **on the backend** into a face embedding (a fixed-length numeric vector) using the recognition library's embedding model; the browser only captures the photo and sends it with the final registration request. The raw photo is stored only on the backend's upload volume for audit/recompute purposes and is **never** sent to the kiosk or any other client.
- The kiosk computes its probe embedding in the browser, so the backend and the browser must run the same embedding model with the same weights (for face-api.js, the same face recognition net producing 128-dimensional descriptors, and the same `@vladmandic/face-api` version on both sides). Vectors from different models or versions are not comparable, and the match would silently fail.
- The kiosk fetches only the embedding dataset (`{ memberId, embedding }` pairs, no images and no names) from a dedicated backend endpoint (`GET /kiosk/embeddings`) gated by a static `KIOSK_API_KEY` (sent in the `x-kiosk-key` header), rather than being open to arbitrary callers. The dataset is every registered member with a password and a reference embedding. It is refreshed in the kiosk every few minutes.
- **Kiosk contract**: after a match the kiosk reports the matched `memberId` with `POST /kiosk/checkins` (same key). The backend answers with one of: `200 { checkInId, turnstileStatus }` (recorded; `turnstileStatus` is `success` or `failed`), `404` (member not found), or `403` with a `reason`. `reason: 'membership_inactive'` means the member's membership is inactive: no turnstile call is made and no check-in is recorded (FR-33, FR-40, RN-15). The kiosk shows "Membership inactive. Please see the front desk." for that reason, and "Access not available" (solid red) for any other answer it does not recognize. A rejected request (network or server error) is its own state, "Check-in unavailable" (dashed): nothing was recorded. The kiosk never receives or displays a member's name. In a non-production build, a development-only endpoint (`GET /kiosk/dev/members`, same key) lists member names so the dev simulation can pick a member; it does not exist in production. Because there is no aptitude gate any more, the earlier `not_cleared` reason no longer applies: the only 403 reason is `membership_inactive`.
- The kiosk counts consecutive no-match or ambiguous results; after 3 in a row it says "Please see the front desk" instead of looping "Try again" (the counter resets after a successful check-in or 3 minutes idle).
- Matching uses a similarity/distance threshold to decide "is this a match at all," plus a margin check between the best and second-best candidate to reject ambiguous ties - the member is asked to retry rather than the system guessing (FR-32).
- This reduces exposure relative to shipping raw photos, but the full embedding dataset is still present in the kiosk's browser memory/network traffic; the kiosk is assumed to run on a trusted, non-public local network for this academic project - a real deployment would need a more hardened kiosk boundary (explicitly out of scope here, see [02-requirements.md](./02-requirements.md)).

## 6. File Storage

- Uploads (the registration reference photo and exam attachments) are written by the backend to a mounted Docker volume (e.g. `/app/uploads`), namespaced by member id. There are no medical certificate uploads: the certificate check happens in person at the gym (FR-57).
- Uploads arrive as base64 inside tRPC inputs (registration happens before any login exists), validated by declared type, file signature, and size: JPEG/PNG up to 2 MB for the reference photo and JPEG/PNG/PDF up to 5 MB for exams. Only the procedures that carry files (registration and onboarding) get a larger request body limit.
- Only the relative path (or a served URL) is stored in Postgres; the backend serves/proxies file reads through an authenticated route rather than exposing the volume directly (`GET /files/*`): an owner reads their own exam attachments, and reference photos are never served to anyone. An exam attachment is optional supporting material kept with its structured entry; the AI never reads it (§4).
- The computed face embedding (not the photo) is what's cached in Postgres and is the only biometric artifact ever served outward, to the kiosk endpoint above.

## 7. Email

- The registration e-mail is sent via a real transactional email API (e.g. Resend) called from the backend once registration completes (FR-9, FR-10). It is fired through a registration-completed hook (a subscriber model: the registration service announces that a member was created, and the e-mail module subscribes), so a failing subscriber is logged and never undoes the registration. The e-mail links to the login page (`WEB_ORIGIN` plus `/login`), not to the onboarding form: after login the member is redirected to onboarding, which is required.
- Requires an API key stored as a backend environment variable; sender domain/config is out of scope of correctness concerns since this is a non-deployed academic project (a sandbox/testing sender is acceptable).
- Onboarding is also reached directly inside the app: a member who has not completed it is redirected to it from every member route on login (FR-11), so email deliverability isn't a hard dependency for completing onboarding. The e-mail wrapper never throws, and `EMAIL_MODE=log` writes the recipient, subject, and text (with the link) to the API log instead of calling the provider.

## 8. Seed Data & Bootstrapping

- A database seed script, run at first boot, first creates the full set of `d_user_policy` rows the app needs, then the `member`, `trainer` and `admin` policy groups with their policy lists, then a fixed set of demo trainer and admin `d_users` rows with known credentials, each given its staff group (documented in the project README) - this is the *only* way trainer/admin accounts and their access come into existence; there is no staff registration UI (FR-41), and beyond this seed the only other way an existing account's policies change is the Admin policy-management feature (FR-43).
- The seed also creates one demo member, `student@example.com`, already registered (membership active, in the `member` group), with `apps/api/src/test/fixtures/faces/valid/reference.jpg` stored as the reference photo and its embedding computed through the same face-embedding module as registration. It lets the member screens be used without going through registration. Like the staff rows, it is insert-if-missing, so a re-run never recreates the photo.
- The same seed script populates the initial exercise/equipment catalog, including the muscle map of every seeded exercise (an existing exercise that has no muscle map yet only gets the map filled in). It runs on every container boot.
- The demo data is a separate, explicit step, `pnpm db:seed:demo` (`apps/api/src/db/seed-demo.ts`, which runs the base seed first). It creates 25 fake members `demo1@example.com` to `demo25@example.com`, every one of which has completed registration (in the `member` group, with stub embeddings and no photo; there are no applicants and no certificates, since neither exists any more). Every fifth member is a lapsed one: an inactive membership whose last check-in and plan are about 10 days ago, as if they stopped paying and stopped coming. Each member has an onboarding submission, plans for the last 21 days plus today (a couple also with a plan for tomorrow, so upcoming plans have something to show) with some trainer-edited ones and review notes, trainer notes on a few of today's plans that the AI reads when it rebuilds them, remembered facts for some members (injuries, medication changes and others, one of them marked as no longer true), and check-ins over the same days with morning and evening peaks plus four in the last 90 minutes. It is idempotent and only replaces the history of its own accounts. The recent check-ins age out of the occupancy window, so it is re-run before a demo.

## 10. Notable Architectural Decisions & Rationale

- **tRPC over REST/GraphQL**: chosen for type-safety across the frontend/backend boundary despite them being separate containers - avoids hand-written request/response types drifting out of sync.
- **Drizzle over Prisma**: explicit client choice for this project (lighter runtime, SQL-close query builder).
- **Kiosk face matching runs client-side**: avoids sending raw face images to the backend for every recognition attempt; only the match result (member identity) needs to reach the backend to trigger the turnstile call. The registration reference embedding is the opposite case: it is computed on the backend, where the raw photo already lives.
- **Embeddings, not photos, reach the kiosk**: the biometric dataset exposed to the least-trusted client (the kiosk) is reduced to numeric vectors rather than raw images.
- **No session store for chat**: keeps the backend stateless per request; durability lives entirely in the structured fact tables, not in a conversation/session table. The proposal draft and the last eight turns of the open chat are held by the browser and sent with each message for the same reason. The server accepts a model answer leniently (only the reply is required) and checks each component on its own, clamping numbers and shortening text and dropping what cannot be used, so one malformed component never turns a reply into an error; a reply cut off mid-answer keeps whatever completed before the cut.
- **The AI proposes, the member applies**: the coach has read-only lookups and no write path; every change it suggests reaches the database only through a member-triggered mutation that re-validates it (`chat.applyDraft`, `profile.confirmFacts`, `plans.updateExercise`), each guarded by the member's own ability. This keeps a prompt injection from becoming a write.
- **No checkout flow**: occupancy is deliberately a rolling-window estimate (FR-37) rather than an exact live count, avoiding the added kiosk complexity of an exit step for no real payoff in an academic demo.
- **Turnstile failures never block check-in recording**: the external API is a best-effort call; the system's own attendance record does not depend on it succeeding (FR-33/FR-34). A failed call is its own state (`failed`), shown to staff in the check-in log (FR-61), never coalesced into a real access decision. The one thing that does stop a check-in is an inactive membership, which is refused before the turnstile is called (RN-15).
- **Membership acceptance happens off-system**: whether a person may become a member is decided in person at the gym by a staff member, who checks the person's restrictions and any medical certificate. The system keeps no record of that check and has no digital screening, so there is no AI verdict, no certificate handling and no applicant state to build or secure (FR-57).
- **The kiosk shows no identity**: results never carry a member's name, because the kiosk is the least trusted, public-facing client; the name is not even in the dataset it holds.
- **Single timezone**: all date/time logic ("today's" plan, the occupancy window, gym-open check) uses the server container's local system timezone - no per-user timezone handling (FR-39).
- **Policy-driven authorization over a fixed role enum**: `d_user_policy` (dimension) + `f_user_policy_on_user` (fact) replace a `role` column entirely (§11). Policy groups (`d_user_policy_group` + `f_user_policy_group_on_user`) are named, seeded bundles of policies, so the Admin sees at a glance who is a member, trainer or admin without a role field: a group is the source of truth with live membership, not a copy of its policies into per-user rows, so a user's group is a stored fact and a change to a group reaches every current member. Granting a new capability, or promoting/demoting an existing account between member/trainer/admin, is a data change (via the Admin policy-management feature, FR-43) rather than a schema migration or a new signup path - `d_users` stays a single table for every person, since access differs by *policy*, not by *profile shape*.

## 11. Authorization (CASL)

Permissions are entirely data-driven - there is no `role` column anywhere. What a user (member, trainer, or admin - all the same `d_users` row shape, see [05-data-model.md](./05-data-model.md)) can do is the union of every non-expired policy currently granted to them directly (`f_user_policy_on_user` → `d_user_policy`) and every policy of each group they currently belong to (`f_user_policy_group_on_user` → `d_user_policy_group_policy` → `d_user_policy`), with a direct `denied` row overriding either, turned into a [CASL](https://casl.js.org/) `Ability`.

**Core (shared, `packages/shared/src/auth/`)**:
- `types.ts` - the closed set of CASL actions (`create`/`read`/`update`/`delete`/`manage`) and subjects (`TrainingPlan`, `PlanReview`, `Catalog`, `ProfileEvent`, `Member`, `CheckIn`, `GymSettings`, `UserPolicyAssignment`, `MemberApp`, `StaffApp`, etc.) both apps build abilities against. There is no certificate subject.
- `abilities.ts` - `defineAbilityFor(user, grants)`, building a CASL `Ability` from a user's resolved policy grants, plus `buildAbilityRules` (the serializable rules `auth.me` returns) and `createAppAbility(rules)` (rebuilds the ability from them) (see [05-data-model.md](./05-data-model.md)'s `f_user_policy_on_user` note for the grant→rule translation).
- `constants/policies.ts` - well-known `d_user_policy.id` string constants (e.g. the ones that mark a user as "a member" for gating purposes, below), and the `d_user_policy_group.id` constants with each group's policy list (`MEMBER_POLICY_IDS`, `TRAINER_POLICY_IDS`, `ADMIN_POLICY_IDS`, which the seed writes into the database), so no module hardcodes a raw policy or group id string.
- Split further by domain (`src/auth/onboarding/`, `src/auth/catalog/`, …), mirroring the backend's domain modules (`rules/backend.md`), rather than one flat abilities file.

**Backend (`apps/api`)**: `src/trpc/context.ts` builds the `Ability` once per request (right after JWT verification) from the requesting user's active grants and group memberships. Routers check `ctx.ability.can(operation, resource)` before calling into the service - this is the only authorization gate; there is no role-based procedure builder.

**Frontend (`apps/web`)**: `src/abilities.tsx` wraps `@casl/react`: it re-exports `AbilityProvider` and exposes a `Can` and a `useAppAbility()` typed to the shared `AppAbility`. `components/auth-guard.tsx` rebuilds the ability once per session from the rules `auth.me` returns (`createAppAbility(rules)`) and provides it via `<AbilityProvider>`. Components either render `<Can I="manage" a="TrainingPlan" />` or call `const ability = useAppAbility(); ability.can('manage', 'TrainingPlan')`.

**The member gate, without a role field**: the registration and onboarding pipeline (FR-1, FR-2, FR-9–FR-14) and the `(member)` route group apply only to a user whose ability includes the member-designated permission(s) (e.g. `read_member_app`, which arrives with the `member` group the moment registration completes, FR-9). The onboarding gate redirects a member who has not completed onboarding to it from every member route. A seeded trainer/admin account belongs to a staff group (`trainer`/`admin`, which carry e.g. `read_staff_app`) instead, and is exempt from the member gate entirely - by construction, not by a special case checking who they are (FR-44). There is no aptitude gate.

**Policy catalog changes in the 2026-10-04 critique** (the full catalog is the `d_user_policy` seed above):
- Added: `manage_own_profile_events` (manage `ProfileEvent`, scope self; in the `member` group) so a member sees the facts the AI remembers and marks them resolved (FR-58); `manage_memberships` (update `Member`; `admin` group) for switching a membership (FR-40); `manage_gym_settings` (manage `GymSettings`; `admin` group) for the opening hours (FR-62).
- Changed: `read_members` (read `Member`) is now also in the `trainer` group, so trainers reach the Members table and the Member page (FR-60). `read_checkins` (read `CheckIn`) stays admin only and gates the check-in log, the turnstile summary and the Gym info hourly detail. `read_catalog` is required to read the catalog list and equipment endpoints (a signed-in user), and `read_gym_info` stays in every group while `/gym` itself is public by design.
- Removed: `review_certificates` (manage `MedicalCertificate`) and the `MedicalCertificate` subject, since the certificate backstop no longer exists.
- Guards worth knowing: `reviews.editPlan` needs `update` on every member's `TrainingPlan` as well as `manage` `PlanReview`, so the admin (who reads every plan but holds neither) is read-only on a review page; the staff Overview needs the read of every member's plans, as the queue does.

## 12. Muscle Map

Muscles are one fixed list shared by every layer, so a muscle id means the same thing in the database, the API, the AI prompts and the screens (FR-49).

- **Shared registry (`packages/shared/src/schemas/`)**: `muscles.ts` holds the 22 muscle ids with their labels and views, the primary/secondary roles and their weights (1 and 0.5), the zod schema for an exercise's muscle map, and the six muscle groups (`MUSCLE_GROUPS`: chest, shoulders, back, arms, core, legs, each muscle in exactly one). `muscle-heat.ts` holds the pure functions: weighted load per muscle from sets and roles, the five heat steps scaled against the busiest muscle, the ranking of muscles, the load summed per group, per-muscle catalog coverage (total, available, lost) and the impact of out-of-service equipment (which exercises and muscles each piece takes out). The API and the web app import the same functions, so a number is never computed two ways.
- **API (`apps/api`)**: the plan view, metrics and the staff demand query (`reviews.overview`) return a weighted load per muscle (`muscleLoad`), computed from `d_exercise_muscles`; the plan view counts only exercises that are performable (FR-17). Catalog coverage is computed in the browser from `catalog.list` with the shared functions, since that response already carries every exercise's muscles, equipment and availability.
- **Web (`apps/web/src/components/muscle-map/`)**: `muscle-paths.ts` holds the inline SVG path data of the front and back bodies, derived from the illustrations in `muscle-map/illustrations/`; both sides of a muscle are painted as one, and the front neck, drawn as an outline, is filled from the closed region inside it. `muscle-map.tsx` draws the bodies (side by side from `sm` or at every width when paired, a front/back toggle on phones, a hover tooltip with the name, value and an injury chip, and a skeleton shaped like the body), `muscle-legend.tsx` explains the ramp, hatch and dashed outline, `muscle-radar-chart.tsx` is the shadcn `Chart` radar of the six muscle groups (a `ChartTooltip` on every point, pointer-only and hidden from assistive technology), `muscle-rank-list.tsx` is the ranked list that doubles as the keyboard path (visually hidden beside the radar, visible where the exact per-muscle number is the point, as in the Overview's Today's demand card), `muscle-load-view.tsx` composes the map, legend, radar or list for any weighted load and shares one hover and one selection between the map and the radar, `muscle-selector.tsx` is the body selector of the add-exercise form, and `muscle-name-picker.tsx` is the dropdown beside it that picks the same muscles by name (grouped by region, searchable, a Primary/Supporting toggle group per muscle). The member's plan panel and the catalog Coverage tab live next to the screens that use them. Heat colors are the `--heat-0` to `--heat-5` tokens in `globals.css`.

## 13. Must-Review Plans, Plan Review Preview, Now and Overview

All of this is derived on every read from tables that already exist; nothing here adds a column or a table (FR-53 to FR-56, RN-14).

- **The rule**: a plan is a must-review plan when its date is today or later and at least one of its exercises fails the FR-17 predicate (`isExerciseAvailable`, RN-04). It is computed in two places that use the same predicate: `plans/service.ts` (`toPlanView`) for the member, and `plans/reviews-service.ts` (`findBlockedByPlan`) for staff. It is never stored and never blocks publication (FR-18); there is no acknowledged state, and no notification is sent. A second reason is derived the same way (FR-71): the plan has an `f_plan_changes` row with a non-empty `acknowledged_warnings` and no `f_plan_reviews` row created after it (`plans/repository.ts`, `findPlanIdsWithAcknowledgedRisk`); a trainer's note or edit afterwards is what clears it, and the `reviews` read paths return it as `riskCount` or `risks`.
- **Member (`plans`, `metrics`)**: the plan view (`plans.getToday`, `plans.getByDate`) gains `needsReview`, `lastEditedAt`, `lastEditedByName` and, for each exercise, `equipmentDown` (the names of its linked equipment that is out of service). The new `metrics.week` returns the days of a range with a check-in and the latest check-in instant, under the same self-scoped read of the member's own metrics as `metrics.mine`. Together with `gym.info` they are everything the Now screen reads. The plan view also carries `trainerNotes` (every note and edit on the plan, oldest first, readable by the member whose plan it is), which feeds the trainer notice on Now (FR-55) and the notes on the plan page.
- **Staff (`reviews`)**: `reviews.queue` entries gain `needsReview`, `unavailableCount` and `noteCount` (plain trainer notes, not the entries an edit leaves behind); the web queue's Trainer tab is every plan with status `trainer_edited` or a `noteCount` above zero, and AI is the rest. `reviews.getPlan` gains `blocked` (the exercises that cannot be done, with the equipment that is down), `recentMuscleLoad` (the weighted load of what the member completed in the 14 days before the plan date), and the member context behind the "What the AI knew" card (the member's name and age, the latest onboarding, and the unresolved remembered facts with their dates and the member's words), plus, for each exercise, whether the member did it. The new `reviews.overview` returns today's date, the number of today's plans (`planCount`) and how many belong to members who already checked in today (`checkedInPlanCount`), `musclePlans` and `muscleCheckedIn` (for each muscle, how many of today's plans, and how many of those from checked-in members, train it through an exercise that can be done), `equipment` (every piece with its `isAvailable`, `planCount`, the number of today's plans that need it, and `checkedInCount`, how many of those plans belong to members already checked in; out-of-service pieces first, then by plan count; a plan counts toward a down piece only through an exercise with no working alternative), the must-review plans with their blocked exercises, and `trainerActivity` (`planCount`, the plans a trainer edited or noted in the last 7 days, `windowDays`, and `latest`, the most recent note or edit across all plans). Everything is counted in distinct plans, never exercise rows or sets. All three are guarded by the same read of every member's plans as `reviews.queue`. The Overview's Turnstile line (admin only) reads `checkins.turnstileSummary` (failed and total check-ins today, and whether a turnstile is configured), guarded by the check-in read permission. The same demand, for another date and without the member's own plan, is what plan generation hands to the AI (§4).
- **Web**: the plan review page (`apps/web/src/app/(staff)/reviews/[planId]/`) computes the plan half of its muscle balance preview in the browser from the exercises being edited and the catalog the response carries, so the preview moves before saving. The member Home, the plan page notice and the staff Overview compose the same shared muscle-map components (§12) and the existing panels; the Now screen has no muscle map.

## 14. API Modules and Page Map

**API modules (`apps/api/src/modules/`)**, each exposing a tRPC router under the name in parentheses:

| Module | Purpose |
|---|---|
| `auth` (`auth`) | Registration (one request: account, password, member group, active membership), login, logout, the session (`auth.me`; no session for an inactive member) and the Members table (`listMembers`, read `Member`) |
